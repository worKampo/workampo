# ADR-0057: Ready for a mobile app

## Context

No mobile code is written, but everything is built knowing that a mobile app will exist and will share as much as possible with the web and the API. Lesson from the previous project: it had the ceremony (CQRS, manual injection, single-implementation interfaces) without the real separation of the domain.

## Decision

**Decision** (2026-11-14): no mobile code is written, but everything is built knowing that an app will exist that shares as much as possible with the web and the API. When it arrives: **option A**, web with Vite and shadcn, and app with Expo, sharing everything except the visual components. A single Expo base for web and mobile is ruled out: it loses shadcn and makes the web worse, especially in accessibility.

- **Already planned**: a single API ([ADR-0006](0006-same-origin-route-map.md), [ADR-0019](0019-typed-contract-with-hono-rpc.md)) with a `fetch`-based Hono RPC client, which also works on mobile; session by `Authorization: Bearer` on mobile ([ADR-0008](0008-own-session-in-d1-host-only-cookie.md)); separate domains ([ADR-0052](0052-living-specs-only-and-flow-by-size.md), [ADR-0053](0053-code-conventions.md)); IDs generated by the app ([ADR-0053](0053-code-conventions.md)); each screen with its own URL (deep links).
- **Done from now on**:
  1. **Pure domain core in `packages/domain/<domain>/`**: Zod schemas, business rules, permissions (`can`, [ADR-0054](0054-roles-and-permissions.md)), error codes and values such as `Email`, `Slug` or `Money`. No data input or output: dependency-cruiser forbids it from importing Hono, Drizzle, React or `fetch`. The API and the web import it, and the mobile app will ([ADR-0053](0053-code-conventions.md)).
  2. **The API only evolves by adding** ([ADR-0019](0019-typed-contract-with-hono-rpc.md)): new fields and endpoints yes; removing or changing the meaning only after a transition period, like expand/contract in migrations ([ADR-0033](0033-expand-contract-migrations.md)). An installed app calls the API with its old version for months. The minimum-version header and the "update the app" screen arrive with the app.
  3. **The session is resolved in a single middleware** that accepts cookie or Bearer ([ADR-0008](0008-own-session-in-d1-host-only-cookie.md)); for now only the cookie is implemented.
  4. **The data layer is shared from day one** (the person, 2026-11-22, ticket 96): the API client, the data hooks (queries and mutations) and the form schemas live in `packages/client/`, which does not touch the DOM (lint rules forbid `react-dom`, `window`, `document`, `localStorage` and `navigator`). The web keeps only screens, routing and wiring; the mobile app will import the same package.
  5. **Design tokens will have a portable source** (TS or JSON) from which the CSS is generated; this is done when the app arrives.
- **DDD and hexagonal, lightweight version**:

| Yes | No |
|---|---|
| The strategic part: domains as separate contexts, common language (`GLOSSARY.md`), each rule in the domain that owns the data ([ADR-0052](0052-living-specs-only-and-flow-by-size.md)) | An interface and a layer for everything with a single implementation |
| Pure core: rules as functions without I/O, tested with simple unit tests | Command and event buses, hand-made dependency injection |
| Thin use cases in the API: load with the repo, call the pure rules and save in a `batch()` | Domain events, until there is async work that needs them ([ADR-0056](0056-async-work.md)) |
| Named aggregates where there is a rule that always holds (company and members: always one owner, [ADR-0054](0054-roles-and-permissions.md)) | Textbook full hexagonal |
| Ports only where something really changes: providers (adapters of [ADR-0053](0053-code-conventions.md)) and the data repo | |

- **For the app's ADR**: what is shared (API types, schemas, permissions, rules, translations and formats, data hooks, tokens) and what is not (visual components, navigation); login with WorkOS on mobile (verify native flow); push; offline mode ([ADR-0002](0002-v1-scope-web-and-d1.md)).

## Consequences

- Ruled out: a single Expo base for web and mobile.
- The minimum-version header, the "update the app" screen and portable design tokens are deferred until the app arrives.
- Pending for the app's ADR: WorkOS native login flow (verify), push, offline mode.
